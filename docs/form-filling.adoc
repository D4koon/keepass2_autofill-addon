= How KeeLink finds and fills login fields
:toc: left
:toclevels: 3
:sectnums:
:source-highlighter: rouge
:icons: font

This document explains how the content script finds login forms on a page,
picks a KeePass entry, decides which page field gets which value, and how you
can see and steer each step. It is written for contributors and for users who
want to understand why a page fills the way it does.

NOTE: The diagrams are PlantUML. They render with
https://docs.asciidoctor.org/diagram-extension/latest/[Asciidoctor Diagram]
(`asciidoctor -r asciidoctor-diagram docs/form-filling.adoc`) or in an editor
with an AsciiDoc + PlantUML preview. GitHub's own AsciiDoc view shows them as
source.

== Overview

Everything below happens in the content script (`src/page/`), separately in
every frame of the page. The background script only relays messages and talks
to KeePass.

[plantuml, overview, svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
title From page load to filled fields

start
:Page loaded or changed\n(page.ts, rescanTrigger.ts);
:Scan forms and loose fields\n(formScanner.ts, formsUtils.ts);
note right
  <form>s, forms in open shadow roots,
  and a stand-in form for inputs
  outside any form
end note
:Keep forms that look like logins\n(formScanner.ts);
if (any login form?) then (no)
  stop
endif
:Ask KeePass for entries\nmatching the page URL\n(background → KeePassRPC);
:Check how each entry fits each form\n(entryRanking.ts, formFit.ts);
:Pick entry and form, decide\nwhether to fill and submit\n(fillDecision.ts);
if (fill now?) then (yes)
  :Assign entry fields to page fields\nand fill them\n(fieldFilling.ts);
  if (submit?) then (yes)
    :Submit the form;
  endif
else (no)
  :Offer the entries in the popup\nand on the field icon;
endif
stop
@enduml
----

The main files:

[cols="1,3"]
|===
|File |Role

|`page/page.ts`, `page/rescanTrigger.ts` |Start the scan, watch the page for changes worth a rescan
|`page/formScanner.ts` |Finds the forms and decides which are login forms
|`page/formsUtils.ts` |Reads a form's fields and guesses the username field (`getFormFields`, `pickUsernameIndex`)
|`page/fieldSignals.ts` |Cheap DOM hints: search box, one-time code, switched off, nearness
|`page/fieldCover.ts` |Hit-test: is something else on the page lying over a field?
|`page/fieldRanking.ts` |Which page field gets which entry field: the rules (`RULES`, `pairFields`)
|`page/formFit.ts` |How an entry fits a form: which form, which entry, fill on page load
|`page/entryRanking.ts` |Ranks entries per form, marks the site's preferred entry
|`page/fillDecision.ts` |Fill or not, submit or not
|`page/fieldFilling.ts` |The fill itself, with the pairs from `fieldRanking.ts`
|`page/fillDiagnostics.ts` |The "Check how this fills here" report
|===

== Finding login forms

=== Which forms are scanned

* every `<form>` in the page,
* every `<form>` inside an open shadow root (web components),
* a *stand-in form* (`Kee-pseudo-form`) holding every input that is in no form
  at all, including inputs inside shadow roots. Many single-page apps (Proxmox
  VE, for example) have no `<form>`; without the stand-in form they couldn't
  be filled.

A form with more than 50 fields is skipped, so dashboards and big settings
pages don't slow every page down.

=== Which forms count as login forms

[plantuml, login-form, svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
title Is this a login form?

start
if (stand-in form?) then (yes)
  :Leave out fields the site config\nblacklists (e.g. name="q");
endif
if (form or a field blacklisted\nby the site config?) then (yes)
  :Not a login form;
  stop
endif
if (has a password field?) then (yes)
  :Login form;
  stop
endif
if (whitelisted by the site config,\nor a field has autocomplete="username"?) then (yes)
  if (has a text field?) then (yes)
    :Login form\n(first step of a two-step login);
    stop
  endif
endif
:Not a login form;
stop
@enduml
----

Blacklist and whitelist are the code's names (`SiteConfig.blackList`,
`whiteList`) for the *Exclude List* and *Include List* in the settings. The
built-in site config (`common/DefaultSiteConfig.ts`) blacklists forms with the
id or name `search` and fields named `search`, `q` or `query` (or with the id
`search` or `q`), so real search forms are never treated
as logins. For the stand-in form only the blacklisted *field* is left out:
otherwise one search box in an app's header would hide every loose login field
on the page.

[[form-fit]]
== Choosing the form and the entry, and filling on page load

`formFit.ts` describes how an entry fits a form in three facts (`FormFit`):

Login field:: What the form offers for logging in, visible and not in the way:
a password field; or, on the first step of a two-step login, the guessed
username field (see <<username-guess>>); or neither. A field that is read-only
or disabled still counts, as some sites unlock their login fields on a click.
Stored field names matched:: How many of the entry's fields have a stored id
or name that a page field matches.
Blocker:: Why the entry isn't filled without a click, if anything (below).

There are no points. Wherever two things are compared, the first rule that
tells them apart decides.

=== Which form

When a page has several login forms (`compareForms`, `bestFormIndex`):

. a password field, before a username field of a first step, before neither
. more stored field names matched (with the entry that fits the form best)
. the one that comes first on the page

=== Which entry

When KeePass returns several entries for the page, they are offered in this
order (`compareEntries`), and the first one is taken:

. the entry marked as preferred for this site
. how exactly an entry URL matches the page, as KeePass reports it: the exact
  page before the same host, before the same domain
. more stored field names matched
. KeePass's order

=== Filling on page load

An entry is filled without a click only if the form passes all these checks;
the first that fails is the blocker:

[plantuml, fill-on-load, svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
title Fill this entry on page load?

start
if (entry set to always auto-fill?) then (yes)
  :fill;
  stop
endif
if (login field?) then (none)
  :wait for a click\n"No login field";
  stop
endif
if (a visible new-password field,\nor two visible password fields?) then (yes)
  :wait for a click\n"Looks like sign-up";
  stop
endif
if (more than 1 other visible, editable\ntext field the entry has nothing for?) then (yes)
  :wait for a click\n"Form asks for more"\n(names the fields);
  stop
endif
if (one matching entry, or several\nand the settings allow that?) then (no)
  :wait for a click;
  stop
endif
if (add-on settings allow auto-fill,\nentry not set to never auto-fill?) then (yes)
  :fill;
else (no)
  :wait for a click;
endif
stop
@enduml
----

The "other fields" are counted after pairing the entry's fields with the page
(<<field-rules>>): visible, editable text fields that got nothing. Hidden
fields, read-only or disabled ones, search boxes, one-time code fields and
fields the site switched off don't count. One such field is allowed
(`MAX_EXTRA_FIELDS`), for a captcha or a "device name" field.

Examples:

* Proxmox VE: user name and password; the search box is in the way and the
  realm and language fields are read-only. Fills.
* Sparkasse: the user name field is visible, the password field hidden until
  the next step, plus a hidden, disabled field for catching bots. The login
  field is the username field. Fills the user name; the password follows on
  the next step.
* A sign-up form with first name, last name, street, user name and a
  new-password field: "Looks like sign-up".
* A profile form with first name, street and a password field: "Form asks for
  more (first name, street)".

An entry that isn't filled on load is still offered in the popup and on the
field icon; a click fills it without any of these checks. The popup shows the
blocker under the entry.

[[username-guess]]
== Guessing the username field

`FormUtils.pickUsernameIndex` picks the text field most likely to take the
username. The guess is used

* to show the username in the popup,
* as rule 7 when filling (see <<field-rules>>),
* when a form is submitted, to decide which value is saved as the username.

Each rule only decides when all rules before it are equal:

[plantuml, username-guess, svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
title Username guess: compare the text fields rule by rule

start
:1. Usable?
 - not inert / aria-hidden (also on an ancestor)
 - not a search box, not a one-time code field
 - when filling: not read-only or disabled
   (on submit sites often lock fields, so not then);
:2. autocomplete="username"?;
if (stand-in form\n(page without <form>)?) then (yes)
  :3. Nearest to a password field;
  :4. Known name or label,\nor autocomplete="email";
else (real <form>)
  :3. Known name or label,\nor autocomplete="email";
  :4. Nearest to a password field;
endif
:5. Before the first password field?;
:6. Closest to the first password field
   (no password field: the first one);
stop
@enduml
----

Details of the signals (`fieldSignals.ts`):

Search box (`looksLikeSearchField`)::
`type="search"`, `role="searchbox"`, inside `role="search"`, the name `q`,
`query` or `s`, or one of the words _search, suche, recherche, buscar, cerca,
zoek, szukaj_ anywhere in the name, id, placeholder, `aria-label` or label.

One-time code (`isOneTimeCodeField`)::
`autocomplete="one-time-code"`.

Switched off (`isSwitchedOff`)::
The field or an ancestor has `inert` or `aria-hidden="true"`, stepping out of
shadow roots. Modal dialogs often set this on the rest of the page.

Known name or label (`isAKnownUsernameString`)::
A fixed list such as _username, user, login, email, e-mail, user name, userid,
benutzername, benutzer, anmeldename_; a trailing colon or asterisk is ignored
("User name:" counts).

Nearness (`stepsToMeet`)::
Walk up from the password field until reaching an ancestor of the candidate.
The fewer steps, the closer the two belong together. The username field meets
the password in the login box; an app's search box only near `<body>`.

Why the order differs on pages without a `<form>`:: The stand-in form spans
the whole page, so a newsletter field named `email` in the footer must not beat
the unnamed field next to the password. In a real `<form>` all fields share
the form anyway, and a field right by the password may be a captcha, so known
names count for more there.

[[field-rules]]
== Which page field gets which entry field

`fieldRanking.ts`. Every pair of page field and entry field whose *types fit*
(text to text, password to password, checkbox to checkbox) is a candidate.
Two candidates are compared rule by rule; the first rule that tells them apart
decides. There are no points.

[plantuml, field-rules, svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
title Comparing two candidates: the first rule that differs decides

start
:1. Matches the id or name stored in the entry;
:2. Is visible;
:3. Matches both the stored id and name;
:4. Matches the stored id;
:5. Is the radio button with the stored value;
:6. Can be reached
   - best: nothing in the way
   - then: covered by something else on the page (hit-test),
     switched off (inert / aria-hidden),
     a search box or a one-time code field
   - last: read-only or disabled;
:7. Is the guessed username field
   (see <<username-guess>>);
:8. Comes first on the page;
stop
@enduml
----

The best candidate is filled, both of its fields drop out, and the best of the
rest is next, until no candidate is left (`pairFields`). So each entry field
goes to one page field, and each page field gets at most one value.

Rules 1 to 5 only decide for entries that store field ids or names, typically
entries KeeLink saved from a submitted form. Entries made by hand in KeePass
store none, and then rules 6 to 8 decide.

Each page field's visibility and reach are looked up once per fill, because
the hit-test forces a layout.

The field icons follow the same order (`limitFields` in `keeFieldIcon.ts`): of
each kind, the two fields an entry suits best get an icon, and among equals the
reachable ones, then the guessed username field, then page order. Locked fields
aren't left out, because they may become editable on a click.

=== Example: Proxmox VE

The login window sits on a mask over the whole app, including its global
search box. The entry stores no field names, so rules 1 to 5 are equal for
every text field.

[cols="3,4"]
|===
|Page field |Outcome

|`pveGlobalSearchField-1020-inputEl` (header) |search box, covered: loses at rule 6
|`view-inputEl` |read-only: loses at rule 6
|`username`, label "User name:" |guessed username: *filled* (rule 7)
|`realm`, `lang` |read-only: lose at rule 6
|`saveusername` (checkbox) |type doesn't fit: no candidate
|`password` |the only password field: *filled*
|===

=== Compared with the old points

Until version 1.0.12 this choice used points: +50 for a matching id, +40 for
a name, +35 for a visible field, +30 for a radio value, 1 to start. A test
(`fieldRanking.test.ts`) compares the rules with the points over every
combination of these facts. They pick the same field except in two rare cases:

* A visible field matching the stored id or name now beats a hidden field
  that matches more of them. Before, the hidden one won.
* A radio button's stored value now counts below an id or name match.

The old −5 for a stored id or name that doesn't match (for databases with the
`KPRPC_FIELD_DEFAULT_NAME_AND_ID_EMPTY` feature) is gone; rule 1 covers it.

Choosing the form and the entry, and deciding to fill on page load, used
points too, plus a "field match ratio" (the share of the form's fields the
entry covers, which had to be over one half). <<form-fit>> replaces them.

== Steering the result

Store the page field's name or id in the entry::
In KeePass, open the entry, tab *KeePassRPC*, *Form fields*, and set the name
or id of the page field for the username and password. A match decides at
rule 1 of <<field-rules>>, ahead of every guess. Entries that KeeLink saved from
a submitted form already have them. Beware of generated names such as
`textfield-1067-inputEl`: they can change when the site is updated.

Always auto-fill::
An entry set to always auto-fill (in its KeePassRPC tab in KeePass) skips the
checks of <<form-fit>>, for pages that still only fill on click.

Include and exclude lists::
In KeeLink's settings, choose *A specific website*, then *Finding forms*. A
form whose id or name, or one of whose text fields' id or name, is on the
*Include List* is always treated as a login form; one on the *Exclude List*
never is (exclude wins). These lists decide about whole forms; they don't pick
a field within a form.

Preferred entry::
With several matching entries, the one marked as preferred for the site is
taken.

== Checking what happened

In the popup, expand an entry and click the *(?)* button ("Check how this
fills here"). The report runs the entry through the same pipeline on the
current page and lists

* whether the entry's URLs match the page,
* each form, whether it counts as a login form, and why not,
* per login form, its login field, the stored field names matched, and
  whether the entry is filled on its own there or what blocks it,
* every field of that form with its type, name, id, label, autocomplete,
  visibility, read-only/disabled, and the signals of section
  <<username-guess>>, which field was guessed as the username, and which were
  filled,
* for each entry field, the page field it went to and the rule that put it
  ahead of the next best one, e.g. `"KeePass username" → #2: beat #0 at rule
  6: can be reached`.

It contains the page address, the entry's title, UUID and URLs, and field
names, ids and labels; never field values or passwords. *Copy* puts it on the
clipboard, ready to paste into a bug report.

[plantuml, diagnosis, svg]
----
@startuml
skinparam shadowing false
skinparam defaultFontName sans-serif
title "Check how this fills here"

actor User
participant "Popup\n(Entry.vue)" as Popup
participant "Background\n(messageHandlers.ts)" as BG
participant "Content script\n(fillDiagnostics.ts)" as Page

User -> Popup : click (?) on an entry
Popup -> BG : entry to diagnose
BG -> Page : Action.DiagnoseFill
Page -> Page : scan, score, force-fill\nthe best form (never submits)
Page -> BG : report lines
BG -> Popup : report
Popup -> User : report with Copy button
@enduml
----

== Tests

* `src/tests/formFilling.matching.test.ts`: form detection, choosing the
  form and entry, filling on page load (sign-up, extra fields, two-step
  logins), the username guess (one fixture page per rule,
  each one the old guess got wrong), the field rules on real pages, the
  stand-in form blacklist, the diagnosis report.
* `src/tests/fieldSignals.test.ts`: the DOM signals, including shadow DOM.
* `src/tests/fieldRanking.test.ts`: the field rules, and their comparison with
  the old points.
* `src/tests/browser/fieldCover.test.ts`: the hit-test in real Chromium and
  Firefox (a modal mask over a search box, a floating label over its own
  field).

When changing a rule, add a fixture page that shows the case, and check that
the test fails without the change.
